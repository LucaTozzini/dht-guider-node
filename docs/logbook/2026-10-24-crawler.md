# Building the crawler

_2026-10-24_ · [← Logbook](./)

First working version of the Milestone 1 crawler: it joins the Mainline DHT, collects info hashes, fetches and verifies their metadata over BEP 9, and stores verified torrents in a local catalogue. Most of the day went into finding out why the first design collected almost nothing, and fixing it.

## Stack

- **Node.js 24 + TypeScript.** The WebTorrent libraries cover the protocol work: `bittorrent-dht` (BEP 5 DHT node), `bittorrent-protocol` and `ut_metadata` (peer wire protocol and BEP 9), `bencode`.
- **SQLite** (`better-sqlite3`) for the catalogue, chosen for its built-in FTS5 full-text search, needed for keyword search in Milestone 2.
- `p-queue` for fetch concurrency, `pino` for JSON-lines logs, `vitest` for tests.

## Catalogue design

One table: `catalogue(info_hash, name, added_at)`. A row is written only after the metadata is fetched from a peer and its SHA-1 matches the info hash, so every entry is cryptographically verified. The name is the torrent's own `name` field (preferring `name.utf-8`): the file name for single-file torrents, the top-level folder for multi-file ones. Crawl progress (pending and failed hashes, rates) stays in memory and in the logs.

One subtlety: `ut_metadata` checks received metadata against the info hash the _peer_ echoes in its handshake, not the one we asked for. A dishonest peer could answer for a different torrent and pass that check, so the crawler rejects peers that echo the wrong hash and verifies against its own hash.

## Finding 1: passive harvesting doesn't work behind a home NAT

The original plan was passive: listen for `get_peers` and `announce_peer` queries from other nodes and record their info hashes. From a home connection, this collected almost nothing.

- A 10-minute probe received **6 incoming queries, all in the first 2 minutes, then none**. The DHT library goes quiet after bootstrapping, so with no outgoing traffic the router's UDP mapping expired. RFC 4787 allows NATs to expire UDP mappings after as little as 2 minutes.
- Adding a keepalive (a random lookup every 30 s) kept traffic flowing, but **all 17 incoming queries over 5 minutes came from nodes we had contacted first, none from strangers**. The router (or the test environment) filters unsolicited packets, so the node is effectively unreachable.
- Result: **5 info hashes in 5 minutes**.

## Finding 2: BEP 51 sampling works through NAT

[BEP 51](https://bittorrent.org/beps/bep_0051.html) adds a `sample_infohashes` query: ask a node directly for a sample of the info hashes it stores. All traffic is outgoing, so NAT doesn't matter, and the spec presents it as the compliant replacement for passive crawling. `bittorrent-dht` doesn't implement it, so the crawler sends it through the library's internal RPC layer and walks the DHT through the nodes each reply returns.

5-minute test:

| Measure                            | Value      |
| ---------------------------------- | ---------- |
| Unique info hashes                 | **24,137** |
| Same run, passive listening        | 12         |
| Replying nodes that support BEP 51 | ~74%       |
| Hashes per supporting reply        | ~20        |
| Queries that timed out or errored  | 39%        |

## Finding 3: lookups were starved

The first end-to-end crawl (sampling → peer lookup → metadata fetch → catalogue) catalogued only **9 torrents in 5 minutes**: 1.1% of finished jobs succeeded, and 95% of failures were "no peers found". Either the sampled hashes were dead, or the lookups were failing.

An experiment separated the two: 150 different sampled hashes per condition, looked up with `get_peers`.

| Condition                        | Found peers | Timed out |
| -------------------------------- | ----------- | --------- |
| Quiet: 4 lookups at once, 10 s   | 79.3%       | 3         |
| Busy: 30 at once + sampler, 10 s | **8.0%**    | **140**   |
| Quiet: 4 at once, 30 s timeout   | 90.7%       | 0         |

So roughly 80–90% of sampled hashes are alive. The bottleneck was the DHT library's default of 16 queries in flight, shared by every lookup and the sampler. Raising it to 128, and pausing the sampler while the fetch queue is full, gave:

| 5-minute crawl               | Before | After     |
| ---------------------------- | ------ | --------- |
| Torrents catalogued          | 9      | **72**    |
| Success rate                 | 1.1%   | **15.5%** |
| "No peers" share of failures | 95%    | 17%       |
| Hashes dropped (queue full)  | 20,375 | 0         |

The main failure now is peers that can't be reached over TCP (224 of 394 failures), likely offline, behind NAT, or uTP-only.

## Finding 4: two of the standard bootstrap routers are down

Cold starts (no saved routing table) got stuck with a single node. Querying the routers directly showed that `router.bittorrent.com` and `router.utorrent.com` didn't answer at all, and the remaining router handed out mostly unresponsive nodes. Adding `dht.libtorrent.org:25401` to the bootstrap list fixed it: cold starts now reach 26–131 nodes within 30 seconds. The saved node list is also merged with the previous one on shutdown, so a run that fails to bootstrap can't wipe a good list.

## State at end of day

- `npm start` runs the full crawler with config from environment variables, a stats line every minute, and clean shutdown. A 90-second run from a cold start catalogued 23 torrents.
- An optional name blocklist keeps tagged content (e.g. "XXX") out of the catalogue.
- 9 offline tests cover verification, fetching, the store, sampling, the blocklist and saved state.

## Next

- A multi-hour unattended run for real discovery and fetch rates.
- Tuning: more concurrent fetches, more peers per hash, and a shorter TCP connect timeout, since most failures are unreachable peers.
